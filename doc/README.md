# دليل توثيق وتنفيذ منصة إدارة القوى العاملة

> هذا المجلد هو نقطة البداية الإلزامية لأي مبرمج أو مساعد ذكاء اصطناعي يعمل على المشروع.

---

## 1. الغرض من مجلد التوثيق

يهدف مجلد `doc` إلى:

- تعريف المشروع ومعماريته وقراراته المعتمدة.
- توضيح ما تم إنجازه فعليًا.
- توضيح ما لم يتم إنجازه.
- تحديد المسار النشط حاليًا.
- تحديد آخر نقطة توقف.
- تحديد أول مهمة يجب تنفيذها.
- منع تكرار تعديل سبق تنفيذه.
- منع إعادة مشكلة سبق إصلاحها.
- منع تعديل ملف معتمد دون سبب أو موافقة.
- منع تنفيذ مرحلة غير معتمدة.
- عزل مسارات الجداول والحوافز والدوام الإضافي.
- تمكين أي مبرمج أو مساعد ذكاء اصطناعي من استكمال العمل دون إعادة التحليل من البداية.
- منع اعتبار وجود صفحة أو ملف أو Route دليلًا على اكتمال الوظيفة.
- توثيق نتائج الفحص والبناء والاختبارات.
- توثيق القرارات التي تحتاج موافقة صاحب المشروع.

## 3. وظيفة كل ملف

### `README.md`

هذا الملف هو دليل استخدام التوثيق.

يحتوي على:

- ترتيب قراءة الملفات.
- طريقة بدء العمل.
- طريقة تسليم العمل.
- تعريف المسار النشط.
- قاعدة مصدر الحقيقة.
- قواعد منع التكرار.
- رموز حالات المهام.
- تعليمات واضحة لأي مبرمج أو مساعد ذكاء اصطناعي.

لا يوضع في هذا الملف:

- تفاصيل النظام الكاملة.
- قائمة المهام التفصيلية.
- سجل التغييرات اليومي.
- مواصفات الجداول أو الحوافز أو الإضافي.

### `PROJECT_CONTEXT.md`

يحتوي على المعلومات الثابتة والمعتمدة عن المشروع، ومنها:

- تعريف المشروع.
- هدف المشروع.
- المعمارية.
- التقنيات.
- مدير الحزم.
- الأوامر الأساسية.
- المسارات الحالية.
- الهوية البصرية.
- قواعد الوقت والتقويم.
- ترتيب مسارات التنفيذ.
- الملفات المعتمدة.
- الإصلاحات السابقة.
- قواعد الأمان والصلاحيات.
- قواعد قاعدة البيانات.
- تعريف اكتمال المهمة.
- سياسة تغيير النطاق.

لا يستخدم هذا الملف كسجل يومي أو قائمة مهام.

### `schedule/SCHEDULE_SYSTEM.md`

يحتوي على المواصفات الكاملة لمسار:

```text
Schedule System
```

وهو المسار النشط حاليًا.

يحتوي على:

- هدف نظام الجداول.
- نطاق النظام.
- المراحل التنفيذية.
- الكيانات المنطقية.
- قواعد منع التعارض.
- قواعد توفر العامل.
- قواعد اليوم الوظيفي.
- قواعد الإقفال.
- الحضور المرتبط بالجدول.
- التمديد والاستثناءات.
- الصلاحيات.
- واجهات API المطلوبة.
- واجهات الاستخدام.
- التقارير.
- الاختبارات.
- تعريف الوصول إلى 99%.
- نقطة البدء الحالية.

### `bonus/BONUS_SYSTEM.md`

يحتوي على المواصفات المستقلة لمسار:

```text
Bonus System
```

حالة هذا المسار حاليًا:

```text
PARKED
```

لا يبدأ العمل عليه قبل:

- وصول Schedule إلى 99%.
- نجاح الفحوصات والاختبارات.
- موافقة صاحب المشروع.

يحتوي على:

- سياسات الحوافز.
- الفئات.
- الشرائح.
- الأهلية.
- تشغيل الحوافز.
- الخصومات.
- التعديلات.
- الاعتمادات.
- التقارير.
- قواعد النسخ التاريخية.
- تعريف اكتمال المسار.

### `overtime/OVERTIME_SYSTEM.md`

يحتوي على المواصفات المستقلة لمسار:

```text
Overtime System
```

حالة هذا المسار حاليًا:

```text
PARKED
```

لا يبدأ العمل عليه قبل فتح بوابته واعتماد صاحب المشروع.

يحتوي على:

- التمديد التشغيلي.
- طلب الإضافي.
- التحقق من الجدول والحضور.
- الاعتماد الكامل والجزئي.
- الحساب المالي.
- نسخة الراتب والساعات المستخدمة.
- أثر الحساب.
- الإقفال.
- التقارير.
- تعريف اكتمال المسار.

### `CHANGELOG.md`

يحتوي على التغييرات التي تم تنفيذها فعليًا فقط.

لكل تعديل يسجل:

- تاريخ التعديل.
- رمز التعديل.
- الملف أو الملفات المتأثرة.
- المشكلة.
- السبب الجذري.
- الحل.
- سبب اختيار الحل.
- نتيجة الفحص.
- نتيجة البناء.
- نتيجة الاختبار.
- حالة التعديل.

لا توضع فيه المهام المستقبلية.

لا يستخدم لتحديد المهمة التالية.

### `DAILY_LOG.md`

يحتوي على سجل كل جلسة عمل.

كل إدخال يجب أن يسجل:

- التاريخ.
- المسار النشط.
- المرحلة الحالية.
- هدف الجلسة.
- ما تم إنجازه.
- الملفات التي تغيرت.
- سبب التعديل.
- نتيجة TypeScript Check.
- نتيجة Build.
- نتيجة Tests.
- نتيجة الاختبار اليدوي.
- العوائق.
- القرارات المطلوبة.
- نقطة التوقف.
- أول مهمة تالية.

آخر إدخال في هذا الملف يمثل نقطة التسليم الرسمية للمنفذ التالي.

### `todo.md`

يحتوي على قائمة التنفيذ الحالية.

يجب أن يحتوي على:

- المسار النشط.
- المرحلة الحالية.
- نسبة الإنجاز المتحقق منها.
- هدف المرحلة.
- المهام مرتبة حسب مراحل التنفيذ.
- حالة كل مهمة.
- العوائق.
- المسارات المتوقفة.
- شروط الانتقال.

يبدأ المنفذ من أول مهمة حالتها:

```text
[ ]
```

بشرط ألا تكون مسبوقة بعائق:

```text
[!]
```

## 4. ترتيب قراءة ملفات التوثيق

أي مبرمج أو مساعد ذكاء اصطناعي يبدأ العمل بهذا الترتيب:

1. قراءة `doc/README.md` كاملًا.
2. قراءة `doc/PROJECT_CONTEXT.md` كاملًا.
3. قراءة ملف المسار النشط.
4. المسار النشط حاليًا هو:

```text
doc/schedule/SCHEDULE_SYSTEM.md
```

5. قراءة آخر إدخال في:

```text
doc/DAILY_LOG.md
```

6. قراءة:

```text
doc/todo.md
```

7. تحديد أول مهمة غير مكتملة وغير محجوبة.
8. مراجعة `doc/CHANGELOG.md` قبل تعديل ملف سبق تغييره.
9. قراءة الكود الحالي المرتبط بالمهمة.
10. عدم كتابة كود قبل فهم الحالة الحالية.

## 5. ترتيب مسارات التنفيذ

ترتيب المسارات المعتمد:

```text
1. Schedule System
2. Bonus System
3. Overtime System
```

لا يبدأ المسار التالي تلقائيًا.

الانتقال إلى المسار التالي يحتاج:

- وصول المسار الحالي إلى 99%.
- نجاح TypeScript Check.
- نجاح Build.
- نجاح الاختبارات الآلية.
- نجاح الاختبار اليدوي.
- إغلاق المشكلات الحرجة.
- إغلاق المشكلات العالية.
- تحديث جميع ملفات التوثيق.
- موافقة صريحة من صاحب المشروع.

## 6. المسار النشط حاليًا

المسار النشط الوحيد:

```text
Schedule System
```

المرحلة الحالية:

```text
S0 — AUDIT
```

الحالة:

```text
ACTIVE
```

النسبة المتحقق منها وفق معيار التوثيق الجديد:

```text
0% VERIFIED
```

هذه النسبة لا تعني عدم وجود كود سابق متعلق بالجداول.

تعني فقط:

- لم يتم تدقيق مسار الجداول كاملًا.
- لم يتم حصر الملفات والجداول والـ APIs.
- لم يتم التحقق من الوظائف بالاختبارات.
- توجد معلومات قديمة متعارضة.
- لا تعتمد أي نسبة قديمة قبل انتهاء مرحلة التدقيق.

---

## 7. قاعدة مصدر الحقيقة

عند وجود تعارض بين معلومتين، يكون ترتيب الاعتماد كالتالي:

1. قرار حديث وصريح من صاحب المشروع.
2. نتيجة فحص أو اختبار حديثة.
3. الكود الحالي بعد قراءته وتشغيله.
4. `PROJECT_CONTEXT.md`.
5. ملف المسار النشط.
6. آخر إدخال في `DAILY_LOG.md`.
7. `todo.md`.
8. `CHANGELOG.md` للأحداث التاريخية فقط.

لا تعتمد:

- نسبة قديمة.
- علامة اكتمال قديمة.
- وصف مكتوب دون كود.
- صفحة موجودة دون API.
- API موجود دون قاعدة بيانات.
- وظيفة موجودة دون اختبار.

## 9. رموز حالات المهام

تستخدم الرموز التالية فقط:

```text
[x] مكتملة ومتحقق منها
[~] موجودة جزئيًا أو تحتاج تدقيقًا
[ ] لم تبدأ أو لم يثبت اكتمالها
[!] عائق يمنع الاستمرار
[-] متوقفة لمسار لاحق
```

### معنى `[x]`

لا تستخدم إلا عندما:

- تم تنفيذ المهمة.
- تم فحصها.
- تم اختبارها.
- تم تحديث التوثيق.

### معنى `[~]`

تستخدم عندما:

- يوجد كود جزئي.
- توجد صفحة دون API.
- يوجد API دون ربط واجهة.
- توجد وظيفة دون اختبار.
- توجد معلومات سابقة تحتاج تحققًا.

### معنى `[ ]`

تستخدم عندما:

- لم تبدأ المهمة.
- أو لم يوجد دليل كافٍ على اكتمالها.

### معنى `[!]`

تستخدم عندما يوجد:

- خطأ يمنع الاستمرار.
- قرار مطلوب.
- مشكلة قاعدة بيانات.
- مشكلة صلاحيات.
- مشكلة بناء.
- مشكلة أمنية.

### معنى `[-]`

تستخدم لمسار أو مهمة متوقفة بقرار.

## 10. قاعدة تنفيذ أي مهمة

قبل تعديل الكود يجب:

1. تحديد المهمة من `todo.md`.
2. قراءة متطلباتها من ملف النظام.
3. قراءة آخر نقطة توقف في `DAILY_LOG.md`.
4. مراجعة `CHANGELOG.md`.
5. قراءة الملفات الحالية المرتبطة بالمهمة.
6. التحقق من أن المهمة ضمن المسار النشط.
7. تحديد الملفات التي ستتغير.
8. تحديد أثرها على قاعدة البيانات.
9. تحديد أثرها على الصلاحيات.
10. تحديد أثرها على الوظائف الحالية.
11. طلب موافقة صاحب المشروع عند التغيير الجوهري.
12. عدم توسيع نطاق المهمة.

بعد تنفيذ التعديل يجب:

1. تشغيل TypeScript Check:

```bash
pnpm run check
```

2. تشغيل Build:

```bash
pnpm run build
```

3. تشغيل الاختبارات المناسبة.
4. تنفيذ اختبار يدوي عند تعديل واجهة أو سير عمل.
5. تحديث المهمة داخل `todo.md`.
6. إضافة التعديل إلى `CHANGELOG.md`.
7. إضافة ملخص الجلسة إلى `DAILY_LOG.md`.
8. تسجيل أول مهمة تالية.

- تغيير مخطط قاعدة البيانات.
- إنشاء Migration جوهرية.
- حذف جدول.
- حذف حقل.
- تغيير نوع حقل قديم.
- حذف أو تغيير API.
- تغيير مسار صفحة.
- تغيير دور.
- تغيير صلاحية.
- تغيير معادلة مالية.
- تغيير قواعد Bonus.
- تغيير قواعد Overtime.
- تغيير تسلسل الاعتماد.
- تغيير قواعد الإقفال.
- إعادة تصميم صفحة معتمدة.
- استبدال حل اجتاز الفحص.
- حذف وظيفة قائمة.
- إضافة مكتبة جديدة.
- إضافة مزود خارجي.
- تغيير مدير الحزم.
- بدء مسار متوقف.
- إضافة ذكاء اصطناعي ينفذ قرارًا نهائيًا.

## 12. الاستثناءات العاجلة

يجوز تنفيذ إصلاح عاجل قبل الموافقة فقط عند:

- فشل بناء كامل.
- فشل TypeScript يمنع العمل.
- ثغرة أمنية مؤكدة.
- خطر فقد بيانات.
- تعطل يمنع تشغيل المشروع.
- عائق مباشر يمنع تدقيق Schedule.

بعد الإصلاح يجب فورًا:

- إبلاغ صاحب المشروع.
- تسجيل التعديل في `CHANGELOG.md`.
- تسجيل الجلسة في `DAILY_LOG.md`.
- تحديث `todo.md`.
- تسجيل نتائج الفحص.

## 13. قاعدة الملفات المعتمدة

لا يعاد تعديل ملف معتمد دون:

- مشكلة مؤكدة.
- متطلب جديد معتمد.
- عائق مباشر.
- ثغرة أمنية.
- خطأ فحص أو بناء.
- موافقة صاحب المشروع عند التغيير الجوهري.

قبل تعديل ملف معتمد:

1. ابحث عنه في `CHANGELOG.md`.
2. افهم سبب الحل السابق.
3. لا تعيد المشكلة القديمة.
4. لا تستبدل الحل دون اختبار.
5. سجل سبب إعادة التعديل.

---

## 14. قاعدة قاعدة البيانات

قبل إنشاء أو تعديل أي جدول:

1. البحث عن جدول موجود يؤدي نفس الوظيفة.
2. قراءة جميع العلاقات الحالية.
3. منع إنشاء جدول مكرر.
4. تحديد أثر التغيير على البيانات الحالية.
5. إعداد Migration.
6. إعداد خطة رجوع.
7. اختبار قاعدة فارغة.
8. اختبار قاعدة تحتوي بيانات.
9. التحقق من عدم فقد البيانات.
10. أخذ موافقة صاحب المشروع عند التغيير الجوهري.

لا ينشأ جدول لأن اسمه ورد في التوثيق فقط.

الأسماء الموجودة في ملفات الأنظمة هي أسماء منطقية، ويجب مطابقتها مع الكود الحالي أولًا.

---

## 15. قاعدة الصلاحيات

- إخفاء زر في الواجهة لا يمثل حماية.
- كل عملية حساسة يجب أن تتحقق من الصلاحية في الخادم.
- أسماء الأدوار يجب أن تكون موحدة.
- يجب مقارنة أسماء الأدوار بين:
  - قاعدة البيانات.
  - Seed.
  - الخادم.
  - الواجهة.
- لا يسمح بتجاوز النطاق التشغيلي من الواجهة.
- مدير النظام لا يعني تلقائيًا تجاوز كل قاعدة دون تسجيل.
- التعديل الرسمي يحتاج سببًا وسجلًا.

---

## 16. قاعدة البيانات التجريبية

لا تستخدم Mock Data في الوظائف النهائية.

يسمح بالبيانات التجريبية فقط داخل:

- Tests.
- Seed خاص بالتطوير.
- Storybook أو نموذج منفصل.
- شاشة موضحة بوضوح على أنها Prototype.

لا يسمح بعرض رقم ثابت على أنه مؤشر حقيقي.

---

## 17. تعريف اكتمال المهمة

لا تعتبر المهمة مكتملة لمجرد وجود:

- صفحة.
- Route.
- زر.
- جدول.
- Procedure.
- Schema.
- بيانات ثابتة.
- تصميم بصري.

تعتبر مكتملة عند تحقق ما ينطبق:

- المتطلب محدد.
- قاعدة البيانات معتمدة.
- Migration ناجحة.
- API مكتمل.
- Validation مكتمل.
- الصلاحيات مطبقة في الخادم.
- منطق الأعمال موجود في الطبقة المناسبة.
- الواجهة مرتبطة ببيانات فعلية.
- حالات التحميل موجودة.
- حالات الخطأ موجودة.
- الحالة الفارغة موجودة.
- سجل التدقيق موجود عند الحاجة.
- اختبار الوحدة ناجح.

## 18. قاعدة تسليم العمل لمنفذ آخر

قبل إنهاء أي جلسة يجب تحديث آخر إدخال في:

```text
DAILY_LOG.md
```

بالمعلومات التالية:

- تاريخ الجلسة.
- المسار النشط.
- المرحلة الحالية.
- المهمة التي تم العمل عليها.
- الملفات التي تغيرت.
- سبب التعديل.
- نتيجة TypeScript Check.
- نتيجة Build.
- نتيجة Tests.
- نتيجة الاختبار اليدوي.
- الأخطاء المتبقية.
- العوائق.
- القرارات المطلوبة.
- نقطة التوقف.
- أول مهمة تالية بالاسم.

لا تكتب عبارات عامة مثل:

```text
أكمل العمل لاحقًا
```

يجب أن تكون نقطة التوقف محددة، مثل:

```text
تم حصر جداول Schedule، والمهمة التالية هي تدقيق العلاقات بين assignments وworkers داخل drizzle/schema.ts.
```

12. عدم استخدام بيانات وهمية في الوظائف النهائية.
13. تشغيل الفحص والبناء بعد التعديل.
14. تحديث ملفات التوثيق.
15. ترك نقطة توقف واضحة للمنفذ التالي.

## 20. أول إجراء حالي

أول مهمة حالية هي:

```text
تشغيل pnpm run build بعد آخر تحديث للوحة التحكم.
```

بعد تسجيل نتيجة البناء:

```text
بدء S0 Audit لمسار Schedule.
```

أثناء S0 يجب حصر:

- ملفات Schedule.
- ملفات Shift.
- ملفات Assignment.
- ملفات Reservation.
- ملفات Attendance.
- ملفات Worker Calendar.
- ملفات Time Balance.
- جداول قاعدة البيانات.
- Routes.
- tRPC Procedures.
- Services.
- Repositories.
- Validation Schemas.
- الصلاحيات.
- البيانات الوهمية.

لا يبدأ إنشاء النظام من الصفر قبل معرفة الموجود فعليًا.
